# Build 75

Bailout loss acquired votes. Build 74 allowed the Build 58 stabilization reserve pool to absorb a Build 73 fund-resolution deficiency after a Build 59 vote or systemic-necessity override. That moved real reserves out of the pool, but the old quota system still treated the loss-bearing member as if nothing new had happened to its institutional stake. Build 75 converts that absorbed reserve loss into governance capital through the Interreality Loss Quota Register.

Every finalized Build 74 `MRT#` transfer is booked exactly once as a Build 75 `LQC#` loss-quota credit. The member whose reserve contribution bore the recapitalization loss receives quota equal to the amount lost. A 0.4719418182 reserve transfer therefore creates exactly 0.4719418182 of new quota for the burden reality.

The accounting is deliberately not a replenishment. Build 75 does not add reserves back to the Build 58 pool, does not increase the old `contributedRA` or `contributedRB` fields, and does not create a new Build 55 monetary asset. It changes only the existing Build 58 member `quota`. Economically, an involuntary reserve loss receives the same amount-for-quota treatment as a voluntary Build 59 quota subscription, but without pretending that fresh cash was subscribed after the loss.

Build 75 immediately recomputes member vote weights with the exact Build 59 quota-score formula: quota plus 35% of historical reserve contributions plus a foreign-reserve term plus exports, less unused drawing rights and stabilization-program borrowing. It updates the actual Build 58 quota vote field and the actual Build 59 director vote field. The old Build 59 autonomous governance loop remains free to update the board's `dominant` flag and emit its own historical creditor-majority event on its next pass.

Each quota booking also creates an `LQS#` vote-shift record. A credit stores the member's quota before and after the absorbed loss, its vote weight before and after, the original Build 74 transfer, recapitalization, and Build 73 receivership references, and whether the loss itself crossed the old Build 59 60% majority threshold.

The first crossing of 60% is recorded as a loss-born majority. Build 75 does not invent a new voting rule; the consequence exists because Build 74 already uses the actual Build 59 director weights. Once the loss-bearing member reaches the old board threshold, that member can supply enough yes votes by itself on a future recapitalization while the bailout target remains recused.

The deterministic current-loss harness starts from a symmetric Build 58/59 system with quota A 10 and quota B 10. A Build 74 transfer of 0.4719418182 RA recapitalizes Reality A using reserves historically supplied by Reality B. Build 75 books one loss-quota credit, moves Reality B quota from 10 to 10.4719418182, and changes votes from 50/50 to A 48.8473447649% and B 51.1526552351%.

The same `MRT#` can never buy quota twice. Re-running reconciliation and directly trying to book the already-recorded transfer leaves quota, credit count, booked count, and total loss-quota amount unchanged.

A threshold harness uses a 5.0 RA Build 74 loss against the same 10/10 starting quotas. Reality B quota becomes 15, the exact Build 59 score gives A 40% and B 60%, and the credit is marked `createdMajority75=true`. An accumulated-loss harness uses three separate 2.0 losses: B moves through 54.5454545455%, then 58.3333333333%, then 61.5384615385%. Only the third credit records the majority crossing.

The cross-build harness executes the exact committed Build 74 and Build 75 logic together. After a 5.0 prior Reality A recapitalization loss gives Reality B 60% of the board, a new 0.5 Reality A deficiency creates another Build 74 recap motion. Reality A is recused; Reality B votes yes with 60 weight; the motion passes as `passed-recap74` with zero no votes and no chair override. The new 0.5 Build 55 facility and monetary base both fall to zero and the pool loses another 0.5 RA. The previous bailout therefore created enough creditor voting power to approve the next bailout.

Build 75 also hardens additive persistence. The authoritative no-double-credit marker is written onto the Build 74 transfer itself. If the isolated v75 state were somehow missing while older Build 58 and Build 74 state survived, Build 75 reconstructs its `LQC#` ledger record and aggregate counters from that transfer marker without increasing quota a second time. The recovery harness used an existing `LQC7` marker for a 0.8 loss; quota remained 10.8, while the v75 ledger rebuilt one 0.8 credit and advanced its serial to 7.

Build 75 persists through `nothing-state-v75`, wraps the existing save/render chain, loads after `multilateral_recap.js`, and extends forget-through-v75. It reads and selectively updates Build 56 reserve context, Build 57 exports, Build 58 quotas/program exposures, Build 59 director votes, and Build 74 transfer history. It does not rewrite the Build 74 transfer amount, refill the stabilization pool, reopen Build 73 receivership, or alter Build 55 money directly.

New places include `reserve loss turning into a board seat fraction`, `the bailout bought votes only after the money was already gone`, `creditor majority assembled from bailout losses instead of new cash`, and `one member able to approve the next bailout because it paid for the last one`. `loss_quota.js` passes V8 syntax validation. The exact committed-function harness covers one-for-one booking, idempotence, majority crossing, accumulated losses, transfer-marker recovery, and a live cross-build proof that Build 75 voting power changes the next Build 74 recapitalization outcome.
