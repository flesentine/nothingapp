# Build 46

The dependency ecosystem acquired governance. Every core package name in Reality A and Reality B now becomes a persistent namespace with a canonical package lineage, a lead maintainer, optional co-maintainers, legitimacy, a succession rule, a generation number, and a governance status. Package names therefore stop being neutral strings: the registry must decide who is authorized to publish the continuation of `runtime-policy`, `quorum-client`, `identity-parser`, `archive-codec`, or `rift-core` when maintainers resign, disappear, fork, or are replaced during an emergency.

Maintainers accumulate fatigue from production usage and vulnerability pressure. A lead maintainer can disappear while old signed binaries and SBOMs continue depending on that namespace, creating an abandoned package without interrupting execution. Co-maintainers can be recruited before that happens. Once a namespace is abandoned or disputed, a succession case can be opened. Downstream packages and currently deployed artifacts then act as an electorate: reverse dependents and production users vote among the previous maintainer, a dependency coalition, and registry or emergency custodians. The winning successor can publish a new package version under the same canonical name, making dependency-graph usage itself a source of maintainer legitimacy.

A registry can also make an emergency takeover, especially when an abandoned namespace has a critical advisory. Emergency stewardship is explicitly recorded as a weaker but operationally effective form of authority. A package can be forked under the same canonical name by a rival maintainer, producing two active lineages that both claim continuity. Governance can recognize one candidate, allow dependencies to vote, or deliberately keep both canonical. Rival releases from the losing lineage can be marked disputed for future resolution without deleting binaries that already contain them.

Canonicalization can be made causally operative by rebuilding live Build 44 artifacts onto the winning package lineage. Those governance-driven rebuilds receive new dependency locks, artifact hashes, provenance attestations, trust-audit entries, and SBOMs; replica assignments move to the new artifacts while the previous binaries and losing package lineage remain historical evidence. Registry governance can therefore change executed software without changing the source commit that originally defined the runtime.

Build 46 tracks package namespaces, maintainers, co-maintainers, maintainer fatigue, abandonment, succession cases, downstream dependency votes, namespace transfers, emergency takeovers, canonical forks, split namespaces, canonicalization decisions, governance-driven production rebuilds, governance legitimacy, and package-governance crises. Crises can create places such as `orphaned package still running the state`, `package name with two governments`, `dependency graph acting as electorate`, `maintainer key holding constitutional office`, and `package registry acting like a succession court`, leaving the bailiff asking the package registry who inherited the namespace.
