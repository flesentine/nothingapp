# Build 69

Recovery protection acquired a clearinghouse. Build 68 closed the gap between Build 67 recovery-note investors and the old Build 53 derivatives dealers, but it deliberately remained bilateral: a Build 63 fund bought recovery-note default protection directly from a Build 53 dealer, and a large payout could default that dealer, break old software swaps, and call collateral chains that existed long before the sovereign-title stack. Build 69 connects those fund-native contracts to the much older Build 54 clearing system through the Interreality Recovery Protection Clearing Service.

Build 63 funds still do not become Build 54 clearing members. Instead they obtain sponsored access through an existing active Build 54 member in the same reality. A Build 68 recovery swap can be novated into a persistent Build 69 cleared position only while the relevant Build 54 clearinghouse is operating or stressed. The seller must itself be an active clearing member, and another active member becomes the fund's sponsor. The fund posts a small risk-sensitive client margin and pays a sponsorship fee from cash. The sponsor dealer receives the fee. The seller's already-segregated Build 68 swap collateral moves into the cleared position instead of being returned to the dealer.

Novation changes the Build 68 swap from bilateral `active` status to `cleared69`. That is important because the older Build 68 reconciliation loop no longer settles the contract directly. Build 69 becomes the settlement authority for the novated contract while preserving the original Build 68 swap, Build 67 note, and Build 52 bond references. If the note repays without default, the cleared protection expires, the client's posted margin returns to the Build 63 fund, and the seller's transferred collateral returns to the Build 53 dealer. The sponsorship fee remains paid.

A Build 67 `defaulted-assignment` or the shared Build 52 bond default creates the cleared credit event. Settlement still owes 60% of protected notional, matching Build 53 and Build 68's 40% recovery assumption, but the payment now runs through a central waterfall. Build 69 consumes the seller's transferred Build 68 collateral first, then the seller dealer's capital, then the seller member's existing Build 54 variation and initial margin. If the obligation remains, it uses the existing Build 54 clearinghouse default fund, then fixed pro-rata assessments against surviving Build 54 members, and finally the clearinghouse's own capital.

This converts Build 68's bilateral contagion into mutualized contagion. If seller resources are insufficient, the seller becomes a defaulted Build 54 member and the clearinghouse becomes stressed. Old active Build 53 swaps sold by that dealer become `counterparty-default` so the existing Build 54 observer can pull them into its own settlement machinery. Any still-uncleared Build 68 recovery swaps sold by the same dealer close against whatever segregated Build 68 collateral remains. The cleared contract itself, however, can continue through the CCP waterfall rather than disappearing with the dealer.

The shared resources are real. Build 69 increments the existing Build 54 member-default, default-fund-use, member-assessment, and failed-settlement state rather than maintaining a parallel fictional clearing balance sheet. A recovery-note hedge derived from a sovereign title dispute can therefore consume the same default fund and dealer capital used to settle software-credit derivatives from Builds 52–54. Solving the bilateral counterparty problem makes an old central counterparty responsible for a risk category that did not exist when it was created.

If the whole waterfall still cannot pay, Build 69 records a `final-with-shortfall` recovery settlement, increments the old Build 54 failed-settlement count, and freezes the clearinghouse. New recovery-protection novations will not enter a frozen CCP. The underlying Build 68 protection failure remains recorded, but the Build 67 recovery note, Build 66 subrogation, and Build 65 title dispute are not rewritten. A centrally cleared hedge can therefore become institutionally final while remaining economically underpaid.

Build 68's double-recovery consequence also survives central clearing. When a non-naked cleared hedge pays at default, Build 69 stores how much the Build 67 note had paid at that moment. If the note later becomes `recovered-after-default`, the later assigned recovery remains a separate cash event and Build 69 records a cleared double recovery. Central clearing changes who guaranteed the default payment; it does not retroactively net that payment against later success of the underlying subrogation claim.

The main deterministic harness used the Build 68 hedge on the 2.2110784 AA recovery note. Sponsored novation moved 0.37367225 of existing seller collateral into the cleared position, required 0.12 of client margin, and charged a 0.03 sponsor fee. With seller dealer capital deliberately reduced to 0.2 and its Build 54 member margin to 0.1, the 1.32664704 default payout exhausted those seller resources and then consumed 0.65297479 from the existing Build 54 default fund. Settlement finished at `final`, the seller became a defaulted clearing member, an unrelated old Build 53 swap became `counterparty-default`, and the fund received the full payout plus return of its client margin. When the recovery note later recovered 2.2110784, Build 69 recorded that later amount separately as a cleared double recovery.

A dedicated mutualization harness removed seller resources, default-fund resources, and CCP capital and left two surviving members with enough dealer capital. They assessed the full 1.2 obligation between them and settlement still reached `final`. A separate exhausted-waterfall harness instead produced only 0.48 of payment against 1.2 due, left a 0.72 shortfall, and froze the CCP. The no-credit-event harness confirmed that normal note repayment returns all client margin and transferred seller collateral; only the 0.03 sponsorship fee remains spent.

Build 69 persists through `nothing-state-v69`, wraps the existing save/render chain, loads after `recovery_derivatives.js`, and extends the forget action through version 69. It reads and selectively updates Build 52 recovery-note bonds, Build 53 dealer capital and old swaps, Build 54 clearinghouses/members/default funds/assessments, Build 63 fund cash, Build 67 recovery notes, and Build 68 recovery swaps. Historical bond defaults, recovery-swap contracts, title losses, insurance claims, and subrogation recoveries remain intact.

New places include `investment fund entered clearing through a dealer sponsor`, `recovery hedge default entering the old software clearing waterfall`, `sovereign title hedge consuming the software clearing default fund`, and `bilateral counterparty risk solved by making everybody share one counterparty`. `recovery_clearing.js` passes Node syntax validation. The instrumented harness executes the actual Build 69 functions and covers sponsored novation, transferred seller collateral, client margin and sponsor fees, seller/member default, Build 54 default-fund use, fixed pro-rata surviving-member assessments, CCP capital loss, final-with-shortfall freezing, old Build 53 counterparty contagion, uncleared Build 68 close-out, normal collateral return, and later cleared double recovery.
